# 푸시 알림 등록 및 표시 QA

## 구현 범위

앱 변경만 포함한다. 서버 API와 payload 정책은 유지한다.

- 로그인 및 저장된 세션 복원 뒤 알림 권한을 확인한다. 첫 요청 전 안내를 표시한다.
- 허용 시 네이티브 기기 토큰을 `POST /push-tokens`에 등록한다. iOS는 APNs 토큰과 `platform: IOS`, Android는 FCM 토큰과 `platform: ANDROID`를 사용한다. `deviceId`는 로그인 때와 같다.
- 앱 복귀, 네트워크 복구, 네이티브 토큰 변경 시 동기화한다. 같은 세션에서 성공적으로 등록한 동일 토큰은 중복 전송하지 않는다.
- 마이페이지의 `알림 설정`에서 미요청 권한을 요청하거나 기기 설정을 연다.
- 로그아웃 시 진행 중 토큰 등록이 끝난 뒤 `DELETE /push-tokens/current`, 서버 로그아웃 순서로 처리한다.
- 식별자만 담은 푸시를 받으면 앱에서 일반 안내 문구의 로컬 알림을 만든다. 업무 본문이나 사진은 배너에 넣지 않는다. 중복 수신은 한 번만 표시한다.
- 배너를 누르면 로그인·매장 접근 게이트를 거쳐 알림 목록으로 이동한다. 상세 접근과 읽음 처리는 기존 목록 흐름을 사용한다.

기준: `../wiki/requirements.md` §6.6, `../wiki/decisions/ADR-004-fcm-delivery.md`, `../wiki/openapi.yaml`의 PushTokenRequest.

## iOS 실기기 확인 순서

1. 이 변경이 포함된 빌드를 설치한다. 기존 배포 IPA에는 새 코드가 포함되지 않는다. 알림 네이티브 모듈과 백그라운드 설정은 기존 구성에 이미 포함되어 있다.
2. 로그인 후 사전 안내에서 `계속`을 선택하고 iOS 권한 창에서 알림을 허용한다.
3. 서버 요청 로그에서 `POST /api/v1/push-tokens`의 200 응답을 확인한다. 기기 ID가 로그인 요청과 같고 등록 상태가 ACTIVE인지 확인한다. 토큰 원문을 보고서나 로그에 남기지 않는다.
4. 해당 계정에 인수인계 또는 일정 변경 알림을 발송한다. 앱 실행 중과 백그라운드에서 일반 문구의 배너가 표시되는지 각각 확인한다.
5. 배너를 누르면 알림 목록이 열리고, 항목을 선택하면 기존 상세 화면으로 이동하는지 확인한다.
6. 같은 notificationId를 재전달해 중복 배너가 생성되지 않는지 확인한다.
7. 권한 안내에서 `나중에`를 선택한 뒤 마이페이지의 `알림 설정`으로 다시 요청할 수 있는지 확인한다. OS에서 거부한 경우에는 설정 앱으로 안내되는지 확인한다.
8. 설정 앱에서 알림을 끈 뒤 앱에 복귀하면 기존 토큰이 비활성화되고, 다시 허용하고 복귀하면 재등록되는지 확인한다.
9. 네트워크를 끈 채 로그인 세션을 복원한 뒤 연결을 복구하면 토큰 등록을 재시도하는지 확인한다.
10. 로그아웃 시 토큰 비활성화가 서버 로그아웃보다 먼저 실행되는지, 다른 계정으로 로그인한 뒤 이전 계정 배너를 눌러 잘못 이동하지 않는지 확인한다.

## 수신 검증의 한계와 장애 분리

현재 서버는 iOS에 `content-available` 기반 조용한 푸시를 보내므로 앱이 수신한 뒤 로컬 알림을 표시한다. iOS는 백그라운드 실행을 제한할 수 있고, 사용자가 앱을 강제 종료한 상태의 배너 표시를 보장하지 않는다. 이 제약은 앱의 권한·토큰 등록 성공과 구분한다.

토큰 등록 200 이후에도 실제 푸시가 도착하지 않으면 서버의 APNs 응답, 앱 서명에 맞는 sandbox/production 환경, bundle ID(topic), background 전송 헤더를 별도 점검한다. 이번 변경에는 서버 수정이 없다.

공식 문서: [Expo SDK 57 Notifications](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/).
